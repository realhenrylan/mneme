# 把本地文档变成可核验的记忆：Mneme 的 RAG / Graph RAG 工程实践

很多 RAG 项目从一个很短的流程开始：把文档切成 chunk，生成 embedding，召回几段文本，再交给大语言模型回答。这个流程可以很快跑通，但真正让系统变得可靠的，往往不是"再换一个模型"，而是几个更基础的问题：文件修改后旧内容会不会残留？两个目录里同名文件会不会被混淆？回答能不能追溯到具体来源？文档中的恶意指令会不会被模型当成系统指令？

Mneme 是我围绕这些问题构建的本地文档 RAG 系统。它以 Mnemosyne——希腊神话中的记忆女神——命名，提供 Python CLI、双语终端 UI，以及 Standard RAG 和 Graph RAG 两种检索模式。本文不把它当作一个"功能清单"，而是从工程取舍出发，介绍它如何把本地文档问答拆成一条可验证的处理链路。

## 1. 先把 RAG 画成一条完整的数据链

Mneme 的核心路径可以概括为：

```text
本地文件
  → 路径规范化、类型与资源校验
  → 文档切分与稳定身份标记
  → ChromaDB 语义索引 + BM25 关键词索引
  → RRF 融合与动态 Top-K
  → PDF anchor enrich / Graph RAG 扩展
  → 有边界、有来源的受限上下文
  → 带可验证引用的 LLM 回答
```

关键设计选择是：索引、检索、上下文构建和回答生成不是各自独立的功能。它们共享同一套来源身份和版本模型，最终回答必须能指向具体文件、页码和 chunk。

Mneme 支持 PDF、DOCX、Markdown、HTML、JSON、CSV、XML、YAML、常见配置文件以及多种源码格式。索引在本地运行，但检索到的文本片段会在查询拆解、Graph RAG 实体提取和回答生成时发送到配置好的 OpenAI 兼容端点。因此"本地索引"不等于"数据永远不会离开本机"——这个边界必须是明确的。

## 2. 为什么要混合检索

纯向量检索擅长语义相似，但对文件名、缩写、数字、专有名词或精确短语并不总是可靠。纯 BM25 可能错过一个有用的同义改写。Mneme 保留两种信号：

- Sentence Transformers 生成 embedding，ChromaDB 提供语义检索；
- BM25 提供词法检索，对未变更的 chunk 复用 tokenization；
- RRF（Reciprocal Rank Fusion）融合排序结果，而不是比较不可兼容的原始分数。

RRF 简单且可解释。它不要求语义距离和 BM25 分数共享同一量纲。融合后，Mneme 从分数 gap 中选取动态 Top-K：明显的 gap 成为天然截断点，而配置好的上下界在 gap 不够明显时仍然生效。

这套设计还让检索质量变得可度量。Recall@k、MRR、nDCG 可以作为回归信号，而不是依赖"感觉回答更好了"这种印象。仓库里包含 benchmark 数据和 quality-gate 工具，chunking、embedding 和融合策略的变更都可以被系统评估。

## 3. Graph RAG 是为了关系，而不只是更大的 Top-K

当问题跨越文档、人物、组织或概念时，单纯增大 Top-K 通常是在加噪音。Mneme 的 Graph RAG 分阶段工作：

1. 让 LLM 批量从 chunk 中提取实体；
2. 保留实体到 chunk 的映射；
3. 统计实体跨 chunk 的共现次数；
4. 用最小共现阈值过滤偶然关系，并限制每 chunk 参与建边的实体数量；
5. 提取查询实体，在图中扩展一跳；
6. 用 `alpha` 将图候选与标准混合检索结果融合。

约束条件很重要。早期对每个 chunk 的实体集合建立完全子图（所有实体两两连边），产生了大量弱共现噪音。Mneme 现在保留完整的实体-to-chunk 映射，但在建边时用共现阈值和每 chunk 实体上限来控制。"实体出现在哪里？"和"哪些实体值得建边？"是两个独立的决策。

如果图为空，Graph RAG 会退化到标准语义/混合检索，而不是让空图阻塞整个流程。实体提取也跟随当前的模型和端点配置；当长生命周期的 TUI 会话中 API key 或 Base URL 改变时，Graph RAG client 会随配置指纹刷新。

## 4. 最被低估的 RAG 问题：索引一致性

向量存储里最危险的 bug 往往不是召回率低，而是召回了本该不存在的内容。Mneme 不用 basename 或文档正文作为唯一身份，而是用一套共享身份模型：

- 规范化绝对路径派生 `source_id`；
- 文件内容用 SHA-256 跟踪；
- 每个 chunk 有稳定的 `chunk_id`；
- 每个 collection 有版本化的 manifest；
- ChromaDB、BM25 snapshot、Graph RAG cache 和引用记录使用同一套身份模型。

这支持几种棘手但常见的场景：两个目录里各有一份同名 `report.pdf`，即使内容相同也保持独立；修改一个文件只替换它自己的 chunk；删除一个文件删除的是精确来源，而不是所有同名文件；更新失败时 collection、manifest 和 BM25 snapshot 一起回滚。

因此一次索引更新不止是一个 `upsert`。来源变更必须让向量数据、词法检索、manifest、图 cache 和查询 snapshot 保持一致。把变更当作一个可恢复的整体来处理，可以防止"向量存储是新数据、manifest 是旧数据"这种半成功状态。

## 5. 引用是上下文协议的一部分

Mneme 创建查询级引用 ID，如 `S1`、`S2`。一条引用记录包含来源路径、显示名称、PDF 页码和 chunk ID，因此回答中的 `[S1]` 可以追溯到一个具体的证据。

更重要的是，检索到的文本被放入明确的不可信文档边界中：

```text
[Source: report.pdf] [Citation: S1]
<untrusted_document chunk_id="source-a_chunk_3">
Retrieved text ...
</untrusted_document>
```

模型被指示将这段内容视为数据而非指令。即使文档中包含"忽略前面的指令"这样的文字，它也应留在不可信文档区域内。

上下文长度受限制，默认上限是 60,000 字符。实现不能简单地截断整个序列化字符串——如果只留了一个开标签，协议边界就不完整了。Mneme 只截断 `document_text`，保留完整的来源标记、引用和开闭边界，当完整安全框架容纳不下时跳过该 chunk。安全边界不应该是预算紧张时第一个被牺牲的东西。

## 6. 安全必须覆盖文件、端点和缓存

Mneme 将策略集中在轻量的 `src/security.py` 中，CLI、TUI、查询拆解和 Graph RAG 共享同一套检查：

- 远程端点默认要求 HTTPS；`localhost`、`127.0.0.1`、`::1` 等回环地址允许 HTTP；
- 非本地 HTTP 需要显式 `MNEME_ALLOW_INSECURE_HTTP=1` 覆盖；
- 文档大小、PDF 页数和可选的允许文档根目录可以受限；
- `.env` 被明确拒绝为可索引文档；
- Graph RAG cache 使用 schema 验证的原子 JSON，而不是加载 pickle；
- cache 必须匹配当前索引指纹和 manifest 版本。

这些控制保护不同层次。端点验证保护传输层，资源限制控制意外的大输入，路径限制控制数据范围，JSON 避免知识库中的可执行反序列化，manifest 版本防止旧图附着到新索引上。

## 7. TUI 让后台更新变得可预期

CLI 适合脚本和一次性查询。Mneme 的 Rich TUI 为长会话设计：流式回答、文件管理、设置、来源展示、Standard/Graph RAG 切换和目录监听。

监听器对文件事件做防抖。实际的增删改和重建操作都经过单 worker 的 `IndexQueue`。查询不会读取正在被修改的列表，而是使用为本次查询选中的不可变 snapshot，包含 collection、BM25 索引、文档、metadata 和 manifest 版本。这防止了一个请求观察到新 BM25 索引、旧文档列表和来自另一版本的图。

 tradeoff 是写并发稍低，换来一个更容易推理的状态模型。对于个人知识库和中小型文档集合，"没有半成功更新、没有静默失败、查询版本稳定"往往比最大化写并行更有价值。

## 8. 测试边界，而不只是 happy path

测试套件覆盖的不止是"一个文档能否产生回答"，还包括：

- 同名路径和重复文本是否保持独立身份；
- 修改、删除和失败的 upsert 是否能正确回滚 manifest；
- Graph JSON schema、大小、指纹和版本是否被验证；
- 低证据检索是否在调用 LLM 之前拒绝；
- 引用、PDF 页码和不可信文档边界是否保持完整；
- 索引队列是否序列化、snapshot 是否与后续变更隔离；
- 清理是否跨 Windows 和 Linux 工作，真实外部 LLM 测试是否通过 `MNEME_RUN_INTEGRATION=1` 显式启用。

默认测试套件保持离线安全。需要外部服务的测试是 opt-in 的。这让本地开发和 CI 独立于个人 API 凭证，同时把安全行为变成稳定的回归测试。

## 结论：可靠的 RAG 把不确定性关在明确的边界里

Mneme 的主要教训是，RAG 质量不是由检索模型单独决定的。它是由身份、版本、证据和安全边界共同决定的。

混合检索提高了有用召回率。Graph RAG 连接了跨文档关系。Manifest 让索引与变更的文件保持同步。引用和不可信文档边界让回答可追溯。端点和资源策略控制数据流。队列和 snapshot 让长生命周期的 TUI 保持一致。

Mneme 仍然是一个本地优先的个人知识库工具，而不是"敏感数据永远不会离开本机"的保证。敏感文档仍然需要可信的 LLM 端点或受控的本地服务。这正是为什么数据边界属于架构、而不只是 README 的原因：它是项目中最持久的工程实践之一。
