## 0. 背景：P1.0 的证据缺口与本设计的对应关系

P1.0 只读诊断（全部证据来自当前源码 + 冻结产物 + 确定性本地复算）得出
`STOP_EVIDENCE_INSUFFICIENT`。本契约设计的唯一目的，是补齐 P1.0 无法
从既有产物中获得的观测，从而判断是否值得预注册一次受控实验。缺口与
捕获内容的对应关系：

| # | P1.0 证据缺口 | 本契约如何补齐 | 对应采集级别 |
|---|---|---|---|
| 1 | 无 dense/BM25 通道级候选 trace，候选召回缺失（4/105 case；candidate_recall 0.845）不可归因 | 每通道候选 `chunk_id`/rank/score 分别记录（在 `rrf_merge` 之前落事件） | Minimal |
| 2 | 无 immutable production query-plan trace，rewrite/decompose 效果不可精确归因 | 记录 rewrite/decompose 结果与规范化 history；Exact replay 另存必要原始规划响应及 SHA | Minimal / Exact |
| 3 | stream 检索宽度 20 vs sync 70，无可比观测（`src/rag.py:2137` 的 `_plan_query_runtime` 注释明确两参数现状：sync 默认 k=70 / stream 20） | 记录 `planning_profile` + 实际 `retrieval_k` + 各阶段候选集合 | Minimal |
| 4 | false-refusal 样本不足（4 FR / 6 SR），无法评估特征化拒答 | 记录 refusal 决策（解析后阈值、top 分数带、理由） | Minimal |
| 5 | selector/拒答阈值扫描已有 NO_GO，不得以同类调参替代证据 | 本设计**不收集**任何用于调参的产物；只记录、不决策、不自动改策略 | — |

禁止事项（P1.0 决策的固定约束）：dynamic top-k、selector
`max_per_source`、拒答阈值/策略、reranker 默认开关、Graph RAG 默认策略、
rewrite/decompose 行为，**均不得因本设计或任何 trace 存在而自动变更**。
任何策略变更必须走独立的预注册受控实验与 promotion gate。

## 1. 明确目标与非目标

### 1.1 目标（只限于回答这五个问题）

1. **通道归因**：dense 与 BM25 各自是否漏召回（正确 evidence 是否根本
   未进入任一通道的候选集，还是进入了但被融合/截断丢掉）；
2. **漏斗定位**：fusion、dynamic top-k、selector、parent/adjacent 扩展、
   refusal 分别在哪个环节造成损失（每环节记录进入/离开集合）；
3. **路径对比**：sync 与 stream 的候选宽度（70 vs 20）和最终 context 差异；
4. **计划归因**：rewrite/decompose 是否在真实多轮会话中改变了检索计划
   （需 Exact replay 级别，见 §2）；
5. **实验前置**：在证据级 + 答案级指标齐备后，判断是否值得预注册一次
   受控实验（promotion gate 见 §6.8）。

### 1.2 非目标（明确不做）

- 不做默认开启的用户行为监控（三级默认 Off，见 §2）；
- 不上传数据——所有 trace 仅存本地用户明确选择的目录；
- 不采集原始文档正文（只存 `chunk_id`、`source_id`、指纹与必要元数据）；
- 不记录 API key、Authorization 头、完整 prompt 中的密钥内容、`BASE_URL`
  端点明文（见 §3.2 身份模型）；
- 不自动更改任何检索策略；
- 不以 trace 存在为由宣称质量已提升；
- 不把 v2.0.11 CANDIDATE、frozen/revisions、synthetic（G1-S）产物当成
  生产 trace——三者与生产观测严格区分（见 §0 与 §4.6）。

## 2. 分级、显式 opt-in 契约（三级）

### 2.1 级别总表

| 级别 | 默认 | 可记录内容 | 不记录内容 | 能回答的问题 |
|---|---|---|---|---|
| **Off** | **默认关闭** | 无持久化 trace（现有内存 metrics 与 LLM 调用记录行为保持不变） | 一切查询内容 | 无 |
| **Minimal diagnostic** | 仅显式 opt-in | plan/profile、通道候选 `chunk_id`/rank/score、融合/selector/refusal/context 决策、配置/索引指纹、分阶段延迟 | 原始文档正文、原始回答、原始模型响应、query/history 原文（只存规范化 SHA 或匿名形式，见 §2.3） | 漏斗定位（缺口 1/3/4）；stream/sync 对比 |
| **Exact replay** | 单独明确同意（在 Minimal 之上逐项勾选） | query、规范化 history、rewrite/decompose 结果、必要的原始规划响应及 SHA | API key、文档全文，除非另有单独批准 | 精确 replay 与 rewrite/decompose 归因（缺口 2） |

### 2.2 Off 级别的硬约束

- 零文件创建（不含既有 metrics/缓存行为）；
- 零额外 LLM/API/网络调用；
- 零回答语义改变；
- 三级切换只影响"是否写 trace"，绝不改变检索/生成代码路径。

### 2.3 Minimal 级别中 query/history 的处理规则（设计决定，不留给实现者）

- 原 query、history 各轮 `(q, a)`、rewritten_query、sub_queries **默认不落
  原文**；只记录：长度、语言脚本（CJK/latin）、`sha256`（含盐，盐由
  consent 会话内随机生成且不落盘——若 owner 后续要求可跨会话聚合，
  须在 §6 另行决定盐的持久化）；
- 例外：owner 在 §6.2 明确批准后，Minimal 可升级记录明文（等价于
  Exact replay 的该字段）；
- 任何字段的明文与哈希不得同时出现在同一事件行（防交叉反推）；
  事件行的字段集按级别固定，不允许实现者按 case 临时增删。

### 2.4 Exact replay 级别必须由 owner 决定的事项（设计不替 owner 决定）

| # | 决策项 | 设计给出的默认建议（可改） |
|---|---|---|
| E1 | 本地存储位置 | 用户主目录下 `.mneme/traces/`（**不得**落入仓库、`src/`、评测/frozen/revisions 树） |
| E2 | 是否加密 | 建议至少对含明文 query/history/原始响应的 segment 做文件级加密（key 由本机凭据管理器保存，不写入仓库） |
| E3 | 保留期 | 建议默认 30 天滚动删除；owner 可另定 |
| E4 | 删除入口 | CLI/TUI 显式 `delete-trace <id>` 命令；删除即不可 replay（见 §4.3） |
| E5 | 访问范围 | 仅本机用户；无任何网络导出/同步路径（本地工具，不是云端遥测） |
| E6 | 是否允许原始模型响应 | 默认**不允许**；只存响应 SHA + 长度 + token 计数。若允许，仅限规划类调用（rewrite/decompose）的响应，且独立于生成类回答响应（生成回答响应默认永不采集） |

### 2.5 用户可见的 consent UX（文案与撤回方式，实现前须 owner 确认）

- 首次进入 trace 相关命令时展示三级说明与当前级别；切换级别需显式确认；
- 撤回 = 切回 Off + 执行删除（见 §4.3）；撤回后新数据零采集，历史数据
  按用户选择的删除范围处理；
- consent 状态记录在本地 consent 文件（含 schema 版本与自哈希），
  **不得**记录任何查询内容。

## 3. 最小事件 schema（版本化）

### 3.1 身份模型（沿用现有稳定 ID，禁止重建）

- `source_id` / `chunk_id`：沿用索引 metadata 中的稳定 ID（`{source_sha256_prefix12}_chunk_{n}` 格式见 `data/v2-corpus/chunks/chunk-manifest.json`）；
- 索引身份：`index_fingerprint` + `manifest_version`（`src/rag.py::index_fingerprint`、`load_index_manifest`）；
- chunks 身份：chunks 文件字节 SHA（与 G1-S chunks contract 同一哈希口径）；
- 配置身份：refusal 阈值解析后值、`RAG_RERANKER` 模式、selector cap、
  context budget 相关配置的指纹；
- prompt 身份：`SYSTEM_PROMPT` 等模板文本的 SHA；
- 模型身份：requested model 名 + served version（当前 `StageProvenance`
  中 served version 固定 `"unknown"`——P1.1 须先解决获取来源，否则如实
  记录 `"unknown"`，不得伪造）；
- **禁止**通过 basename 或正文匹配重建任何身份。

### 3.2 事件分组与匿名化

- 标识：`trace_id`（随机 UUID，与用户无关联）、`session_id`（进程内
  consent 会话）、`turn_index`（会话内序号，可从 0 或随机偏移开始——
  偏移方式由 owner 决定，默认随机偏移以防推断会话长度）；
- 敏感字段分级标记：每行含 `pii_level` 字段（`none` / `hashed` /
  `plaintext_owner_approved`），并随级别校验（§2.3）；
- 不记录：API key、Authorization、`BASE_URL` 明文（只记 endpoint 校验
  结果布尔值）、文档全文、生成回答正文（除非另有单独批准且仅限规划
  响应，见 §2.4 E6）。

### 3.3 事件类型（`event_type` 枚举，v1）

| event_type | 字段（除公共头外） | 采集级别 |
|---|---|---|
| `trace.begin` | `planning_profile`（sync/stream）、`retrieval_k`（实际值）、consent 级别、配置指纹 | Minimal |
| `rewrite.decided` | guard 结果、是否调用 LLM、outcome（与 `StageProvenance.outcome` 同枚举）、`requested_model`、temperature/max_tokens/timeout/retries_used、结果 SHA（query 原文按 §2.3） | Minimal |
| `decompose.decided` | 同上 + sub_query 数量与各自长度/语言（原文按 §2.3，Exact 可存明文） | Minimal |
| `retrieve.dense` | 每 sub-query：候选 `chunk_id` 有序列表（前 N）、rank、distance score | Minimal |
| `retrieve.bm25` | 同上：候选 `chunk_id`、rank、BM25 score | Minimal |
| `fusion.rrf` | 融合后有序候选（`chunk_id` + RRF score）、剔除的 BM25 零分条目数、anchor 加权命中数 | Minimal |
| `merge.rewrite_drift` | `merge_log`（original_count/rewrite_count/merged_count/rewrite_only/original_only/overlap_count，与 `src/rag_query_rewriter.py::merge_rewrite_results` 同字段） | Minimal |
| `cutoff.dynamic_top_k` | 进入的候选序列长度、cut 位置、min/max_k | Minimal |
| `refusal.decided` | `retrieval_refused` 结果、解析后生效阈值（与 `src/rag.py::retrieval_refused` 同一解析逻辑）、top 分数带（top1/top2/mean5）、reason | Minimal |
| `rerank.applied` | 是否启用（默认 none）、模型名（若启用）、rerank 前后 top_k | Minimal |
| `selector.applied` | 每候选 `chunk_id` 的保留/跳过原因（`top_k_cut` / `max_per_source` / `kept`）、cap 值、top_k 值 | Minimal |
| `expand.parent_adjacent` | 每候选的 parent 替换/相邻扩展记录（`chunk_id` 级别）、最终集合 | Minimal |
| `context.built` | `context_k`、实际进入 prompt 的 `chunk_id` 有序列表、字符预算截断是否触发、总字符数 | Minimal |
| `generation.completed` | 结果 SHA（不存正文）、token 计数、latency、error_category、citation 状态（`state`/`valid_ids`/`invalid_ids`/`missing`——**只作为结果字段，不得伪称语义正确**）、refusal/API 错误终态 | Minimal |
| `trace.end` | 结束原因（正常/中断/错误）、各阶段耗时汇总 | Minimal |

- 公共头：`schema_version`、`trace_id`、`session_id`、`turn_index`、
  `event_type`、`pii_level`、`line_sha256`（见 §3.4）、时间戳不入
  canonical 行（防重放歧义），另存于 receipt。
- Exact replay 额外事件：`plan.raw_response`（仅规划类调用，owner E6
  批准后）、`query.plaintext` / `history.plaintext`（owner 批准后）。

### 3.4 封存格式（与 G1-S seal 字节约定同源但独立演进）

- JSONL 行：`ensure_ascii=False, sort_keys=True, separators=(",", ":")` +
  显式 LF（Windows 上写字节而非 `write_text`）；
- 行哈希：剔除自身 `line_sha256` 字段后的 canonical 行 SHA（与 G1-S 同
  策略）；
- 批次：`trace.segment.jsonl` + `trace.manifest.json`（含有序行哈希、
  文件字节 SHA、manifest 自哈希、输入/输出闭环 receipt、schema 版本）；
- 本 schema 为 `production-observability` 命名空间，版本独立于
  G1-S `CAPTURE_SCHEMA_VERSION`（v1 起步）。

## 4. 不可变、可删除与 replay 规则

### 4.1 默认关闭的零效应

Off 时：零文件创建、零额外 LLM/网络调用、零回答语义改变（与现状逐字节
一致——现状为：内存 metrics ring buffer 与 LLM 调用记录均为既有行为，
不因本契约变化）。

### 4.2 存储边界（运行时强制）

- trace 只能写入用户明确选择的本地目录（§2.4 E1）；**禁止**写入仓库、
  `src/`、`plans/`、评测/frozen/revisions 树、G1-S 输出根；
- 路径校验在每次写前执行（resolve 归一 + 白名单比对），非法即
  capture 失败但回答不受影响（§5）。

### 4.3 不可变与删除

- 每个已封存 segment（batch）以行哈希 + manifest 自哈希闭环；历史
  segment 只追加新 segment，**禁止原地改写**；
- 删除是用户可见操作，按 `trace_id` 或 `session_id` 范围执行；删除后
  在 manifest 侧记录 `deleted_at` 墓碑与"该 trace 不可 replay"事实
  （墓碑不含被删内容，仅含 ID 与时间）；
- 删除后发起的 replay 请求必须返回明确错误（§5 末行）。

### 4.4 Replay 规则

- Exact replay **默认零 LLM**：注入已记录 plan（rewritten_query /
  sub_queries / base_candidates），复用
  `prepare_answer_evidence(query_plan=...)` 的既有注入点
  （`src/rag.py:2260` 起的 `query_plan` 分支），不重新请求模型；
- 规划类 stage 若想复算（非默认）：需要 owner E6 允许原始响应存在，
  否则 replay 只能做"结果重放 + 下游确定性重算"；
- replay 前身份校验（逐项，见 §4.5）：chunks、index、config、prompt、
  model；任何一项漂移按 §4.5 处理。

### 4.5 漂移处理边界（逐项定义）

| 漂移项 | 处理 |
|---|---|
| chunks 文件字节 SHA 不一致 | **fail-closed**（拒绝 replay）——与 G1-S chunks contract 同策略 |
| index 指纹（`index_fingerprint`/`manifest_version`）不一致 | **fail-closed**（候选集身份不可信） |
| config（refusal 阈值解析值 / selector cap / reranker 模式）不一致 | **warning-only**（下游确定性重算仍可比，但结论须标注配置差异） |
| prompt 模板 SHA 不一致 | **fail-closed**（生成结果不可比） |
| model requested 不一致 | **warning-only**；served version 为 `"unknown"` 时不比较（沿用 G1-S.1 合同修正 B） |
| history 内容不可获得 | Exact replay 降级为 Minimal 重放（只重算检索漏斗），并显式标注 |

### 4.6 与 synthetic harness（G1-S）的隔离

- `src/query_plan_capture.py` 保持 `CAPTURE_MODE = "synthetic_only"`，
  不改造为生产采集器；
- 生产 trace 与 synthetic capture 不共享 capability、输出目录、受保护
  资产边界或 schema 版本；
- 任何把生产采集器放进 G1-S harness 的做法都是越界。

## 5. 安全、性能与失败模式

原则：**生产回答永远优先于可选观测**。capture 失败只影响 capture，
不影响回答，不泄露内容，不静默改变策略。逐类定义：

| # | 失败模式 | 是否阻断回答 | 是否仅阻断 capture | 是否允许 replay | 用户可见提示 |
|---|---|---|---|---|---|
| 1 | consent 缺失（Off 或未初始化） | 否 | 是（零写入） | 否 | 无（静默零采集） |
| 2 | 存储路径非法（落入受保护树） | 否 | 是（fail-closed，不写） | 否 | 一次性日志警告（不含内容） |
| 3 | schema 版本不兼容 | 否 | 是 | 否（拒绝旧版本 replay） | 提示升级/迁移 |
| 4 | trace 写入中断（断电/异常） | 否 | 是（当前 segment 作废，不补写） | 仅完整封存 segment 可 replay | 下次启动提示"上次 trace 未封存，已丢弃" |
| 5 | manifest/receipt SHA 不一致 | 否 | 是 | 否（fail-closed） | 提示"trace 完整性校验失败" |
| 6 | chunks/index/prompt 漂移 | 否 | 不适用 | 按 §4.5（fail-closed / warning-only） | 拒绝或标注后给出 replay 报告 |
| 7 | 原始内容不可获得（被删/未批准） | 否 | 不适用 | 降级或拒绝（§4.4/§4.5） | 提示缺哪类输入 |
| 8 | stream 中断 / LLM transport error / 拒答 | 否（正常错误路径） | 否（仍记录事件，标记错误终态） | 是（作为错误终态重放） | 沿用现有产品错误提示，不加新提示 |
| 9 | storage 满 / 权限失败 | 否 | 是（放弃写入，不重试风暴） | 否 | 一次性提示"磁盘不足/无权限，观测已停用本次" |
| 10 | trace 删除后的 replay 请求 | 否 | 不适用 | 否（明确报错"trace 已删除"） | 报错信息不含被删内容 |

补充：capture 的 I/O 必须在检索/生成热路径之外（异步或尾随写入），
写入失败不得抛入回答路径；并发控制沿用 gateway 既有模式
（进程级锁 + 上限），不新增全局可变状态暴露给回答逻辑。

## 6. P1.1 owner 决策记录（2026-08-17）

本次 owner 授权固定采用 Minimal-only：默认 Off、仅显式 consent 后本地写入；Exact replay 与所有原始 query/history/rewrite/decompose/answer/model response 均禁止；保留期 30 天；路径为 `MNEME_DATA_DIR/traces`；允许 sync/stream 对照；无网络导出；性能目标为检索额外开销 <5% 且不阻塞 TTFT；promotion 永不自动触发。撤回停止新采集，删除通过受限单 trace/过期清理完成。Graph 不接入，`src/query_plan_capture.py` 保持 synthetic-only。


> 以下各项**必须**由 owner 明确选择；设计不替 owner 猜测。未全部决定前，
> 不得实现真实 production capture。

| # | 决策项 | 选项/待定 |
|---|---|---|
| 1 | 是否允许 exact replay（含明文 query/history/plan 响应） | 允许 / 只允许 Minimal / 暂不 |
| 2 | raw query / history / rewritten_query / sub_queries / raw model response 各自是否允许保存 | 逐项 允许 / 仅哈希 / 禁止 |
| 3 | 本地路径、加密、保留期、删除方式 | §2.4 E1–E4 逐项确认或修改 |
| 4 | consent UX 文案与撤回方式 | 批准 §2.5 或提供修改 |
| 5 | 是否允许收集 stream/sync 对照 | 允许（Minimal 即可） / 不允许 |
| 6 | 可接受的性能开销 | 例如：capture 增加 <5% 检索耗时、写入异步不阻塞 TTFT |
| 7 | 收集到何种样本量或触发条件后，才允许发起下一次受控实验 | 例如：≥N 个含 channel trace 的 case 且 ≥M 个 Exact replay case |
| 8 | 哪些 answer-level 指标是实际 promotion gate | 例如：point coverage / citation validity / false-refusal 率——预注册实验的判据 |

## 7. P1.1 的停止与进入条件

```text
P1.1-G0_DECISION =
  READY_FOR_OWNER_CONSENT
  | STOP_PRIVACY_DECISIONS_REQUIRED
  | STOP_REPLAY_CONTRACT_INSUFFICIENT
```

- `READY_FOR_OWNER_CONSENT`：本契约经 owner 审阅，§6 决策表全部填写
  完成后，才允许进入 P1.1 实现（先写 RED 测试的 TDD，范围仅限
  capture/replay/删除 UX，不改任何检索策略）。
- `STOP_PRIVACY_DECISIONS_REQUIRED`：owner 未对敏感数据（明文 query/
  history/原始模型响应）、留存与删除做出明确决定——此时**不得**实现
  真实 production capture，可继续做不涉及敏感数据的准备工作
  （如 schema 常量、纯函数测试骨架）。
- `STOP_REPLAY_CONTRACT_INSUFFICIENT`：§4 的不可变/删除/replay 规则
  在评审中发现缺口——返回本设计修订，不进入实现。

无论哪种停止，以下事实不变：默认产品策略（dynamic top-k / selector /
拒答 / reranker / Graph / rewrite-decompose）未被本阶段或后续 P1.1 的
观测工作自动改变。
